# AI·Data R&D Flow

CDX 사업담당자의 **개인 사업관리 워크스페이스**.

전통적인 R&D PM 툴이 아니다. 목표는 하나다 — **오늘과 이번 주에 내가 뭘 해야 하는지 알려주고, 흩어진 업무를 자동으로 정리하는 것.**

```
자연어 한 줄  →  자동 분류(8개 영역)  →  오늘 / 이번 주 / 이번 달
WBS 엑셀      →  현재 상태 요약(지연·주의·확인사항)
RFP 원문      →  키워드 검색 → 몇 쪽에 있는지 바로 확인
등록된 업무    →  오늘 보고할 것 선별(룰) → 보고 문장(로컬 LLM)
회의록        →  안건별 쟁점·결정·후속조치 → 1페이지 보고서
```

---

## 화면

| 화면 | 하는 일 |
|---|---|
| **개요** | 연구개발 현황 한 줄 요약 + 빠른 입력 + **오늘 / 이번 주** 업무 (이번 달은 접어둠) |
| **업무트리** | 사업담당자 업무를 8개 영역으로 나눈 개인 업무체계 |
| **연구개발 현황** | WBS 엑셀을 넣어 지금 상태만 요약 (회차 비교 없음) |
| **기관별** | 회의·통화 직전에 여는 기관 원페이지 (진척·지연·미결 요청·이력) |
| **RFP 검색** | RFP 원문을 넣고 필요한 문구가 몇 쪽에 있는지 검색 |
| **보고 생성** | 일일 업무보고 · 이메일 · 재촉 · 회의록 · 인수인계 · 주간업무계획 (로컬 LLM) |

**메뉴는 일이 아니라 자료를 기준으로 나눈다.** 앞의 세 화면은 담당자가 매일 보는 것(내 업무·연구개발 현황)이고, 뒤의 두 화면은 문서를 넣어야 열리는 것(RFP·회의록)이다. 그래서 별도 보고서 페이지나 인박스 메뉴는 두지 않았다 — 업무 입력은 개요의 빠른 입력창에, 보고자료 작성이라는 *업무*는 업무트리의 한 영역에 있다.

`보고 생성`은 그 업무를 대신하는 메뉴가 아니라 **이미 등록된 업무·회의록을 문장으로 바꿔 주는 도구**다. 무엇을 보고할지 고르는 일은 여전히 업무트리와 우선순위 규칙이 한다.

---

## 1. 빠른 입력 — 폼을 채우지 않는다 (`lib/capture.ts`)

한 줄 적으면 분류·기관·기한·상태가 한 번에 채워진다.

```
A기관에 데이터 3종 아직 안 왔음. 금요일까지 다시 확인
  → 데이터 제공·수급 관리 · A기관 · 2026-08-14 · 확인 필요

다음 월간회의 전에 B기관 모델 성능자료 받아야 함
  → 회의 운영 및 후속조치 · B기관 · "다음 월간회의 이전" · 요청 필요
```

두 가지를 지킨다.

**날짜를 지어내지 않는다.** "다음 월간회의 전"처럼 날짜로 못 바꾸는 기한은 억지로 변환하지 않고 표현 그대로 남긴 뒤, 우선순위 계산에서는 "회의 전 확정 필요"로 다룬다.

**행동이 상태를 이긴다.** "아직 안 왔음. 다시 확인"에는 상태(회신 대기)와 행동(확인)이 같이 있다. 담당자가 보고 싶은 건 다음에 뭘 할지이므로 행동을 상태로 잡는다.

여러 줄을 붙여넣으면 줄마다 한 건씩 등록된다.

## 2. 업무트리 — 내 업무체계 (`lib/worktree.ts`)

연구기관의 WBS가 아니라 **내가 해야 하는 일**의 구조다. 8개 영역으로 고정한다.

```
데이터 제공·수급 관리 · 회의 운영 및 후속조치 · 연구기관 진도관리 · 실증·성과관리
마일스톤·공식 일정 관리 · 예산 대응 · 보고자료 작성 · 기타 / 미분류
```

**카테고리를 늘리지 않는 것이 규칙이다.** 애매한 입력은 새 분류를 만들지 않고 '기타 / 미분류'로 보낸다 — 분류 체계가 불어나는 순간부터 안 쓰이게 된다.

각 영역에는 담당자가 늘 챙기는 **상시 점검 항목**이 체크리스트로 붙어 있고, 실제 등록한 업무만 개요의 오늘/이번 주에 올라간다.

### 기관 마스터 11개 (`lib/org.ts`)

카테고리와 같은 이유로 **기관도 11개에서 늘리지 않는다.** 자유 입력을 허용하면 "지엠티",
"㈜지엠티", "GMT"가 각각 다른 기관으로 쌓여 기관별 집계가 조용히 무너진다.

| 기관 | 역할 |
|---|---|
| 지엠티 | 주관연구기관 |
| 유원GIS · 세명소프트 · 그린블루 · 엑셈 · MIT · 동국대 · T3Q · 써로마인드 | 공동연구기관 |
| KIMST | 전문기관 |
| 기타 / 미분류 | 폴백 |

2~9번은 통합 WBS의 기관별 시트명에서 그대로 가져와 **상수로 고정했다.** 매번 파일에서
읽지 않는다 — 파일이 바뀌면 기관이 조용히 늘어나기 때문이다. 실제 WBS(226개 항목)를
파서에 통과시켰을 때 뽑히는 기관 9개가 마스터와 정확히 일치한다.

```
입력 문장
  → 별칭 일치(공백·㈜·괄호 제거 후)  → 해당 기관
  → 후보 2곳 이상                    → '기타'로 보내고 후보를 함께 표시
  → 미매칭                           → '기타'
```

**후보가 둘이면 고르지 않는다.** 반반 확률로 찍는 것보다 사람이 고치게 하는 편이 낫다.

**영문 약칭에는 단어 경계를 요구한다.** `MIT`를 부분일치로 잡으면 `submit`·`limit`에
걸려 엉뚱한 기관이 붙는다. 한글 별칭은 부분일치로 충분하다.

기관별 회신 임계일도 여기 둔다(주관 3 · 공동 5 · 전문 7영업일). 회신 대기가 얼마나
지났는지 판정할 때 쓴다.

빠른 입력의 대상기관은 **선택 목록**이다. 자유 입력 칸을 두지 않았고, 화면에서 기관을
추가하는 UI도 만들지 않는다 — 기관 추가는 코드 수정 사항으로 둔다.

## 3. 우선순위 자동화 (`lib/mytask.ts`)

사용자가 매긴 우선순위만 믿으면 결국 전부 '높음'이 된다. 그래서 사실에서 점수를 만들고, **그 근거를 화면에 그대로 띄운다.**

| 축 | 예 |
|---|---|
| 기한 | 초과 · 오늘/내일 · 7일 내 · 한 달 내 |
| 회의 연계 | 다음 회의 전 확정 필요 |
| 연구개발 연계 | 지연된 과업에 직접 영향 |
| 회신 대기 | 외부기관 응답을 기다리는 중 |
| 보고·예산 | 보고자료·예산 대응 |
| 반복 지연 | 2회 이상 미뤄짐 |

결과는 **긴급 / 이번 주 중요 / 일반** 세 단계다. '미루기'를 누르면 기한이 일주일 밀리면서 미룬 횟수가 쌓인다 — 반복해서 밀리는 일이 드러나야 한다.

시간 분류는 **오늘 → 이번 주 → 이번 달** 순이고, 기한이 지난 일은 '오늘'로 올린다. 이번 주 카드가 화면에서 가장 강조된다.

### 이벤트 로그 — 왜 이렇게까지 밀렸는가 (`lib/history.ts`)

"몇 번 미뤘나"를 숫자 하나로 들고 있으면 **왜 이렇게까지 밀렸는지**를 답할 수 없다.
담당자가 바뀌는 시점에 가장 크게 유실되는 것이 바로 그 경위다.

그래서 사건을 그대로 쌓는다. `created` · `due_changed` · `status_changed` · `sent` ·
`replied` · `reminded` · `closed` 일곱 가지다.

**append-only다.** 이벤트는 고치지도 지우지도 않는다. 업무를 지워도 `closed`로 남긴다.
그리고 화면에 쓰는 값은 **전부 파생값으로 계산한다** — 저장하는 순간 사건과 요약이
어긋나기 시작한다.

| 파생 지표 | 쓰는 곳 |
|---|---|
| `postponeCount` | 우선순위 가점 · "3회 연기" |
| `totalSlipDays` | "당초 6월 30일 → 현재 9월 30일" |
| `daysSinceContact` | 회신 대기 영업일 · 재촉 판정 |
| `awaitingReply` | 미결 요청 목록 |
| `reminderStage` | 재촉 문체 강도(1차 확인 → 2차 기한 → 3차 경위) |

우선순위에는 **더하기만 한다.** 기존 배점은 건드리지 않았다. 2회 연기 +10, 4회 이상
+10, 누적 30일 이상 +10, 회신 임계일 초과 +15이고 근거 문구가 기존 근거 영역에 그대로 붙는다.

**영업일 계산은 따로 시험한다.** 임계일 판정이 전부 여기 걸려 있는데 주말 처리는 조용히
틀리기 쉽다. 금요일에 보내고 다음 월요일이면 1영업일이고, 보낸 날 당일은 세지 않는다 —
아침에 보낸 요청을 그날 오후에 "1일 지났다"고 재촉할 수는 없다.

**공휴일은 아직 넣지 않았다.** 음력 명절처럼 해마다 바뀌는 날짜를 코드에 박아 두면
이듬해에 조용히 틀린다. 지금은 주말만 세고, 필요하면 호출부가 날짜 목록을 넘긴다.

## 4. 연구개발 현황 (`lib/wbsStatus.ts`)

회차 간 비교는 하지 않는다. 담당자가 알아야 하는 건 "지난주 대비 뭐가 바뀌었나"가 아니라 **"지금 어떤 상태이고 뭘 확인해야 하나"** 이기 때문이다.

지금 파일 하나만 보고 판단할 수 있는 것만 뽑는다 — 전체 진행률(계획 대비), 지연 중인 항목, 주의가 필요한 항목, 진행 중인 과업, 완료 과업, 기관별 상태, 그리고 **확인해야 할 사항**(실적 미입력·착수 지연·산출물 임박·일정 미기재).

### 실제 기관 WBS 읽기 (`lib/parseFile.ts`, `lib/wbs.ts`)

실제 공공 R&D 통합 WBS는 단일 표가 아니다. 검증에 쓴 파일(2차년도 통합 WBS, 226개 항목/9개 기관)은 이런 구조였다.

| 실제 구조 | 대응 |
|---|---|
| 기관별로 시트가 9개 + 총괄·마일스톤·코드매핑 | 시트를 하나 고르지 않고 **과업 시트를 전부 찾아 합침** |
| 시트마다 위에 제목·안내 행 2~3줄 | 헤더 행을 20행까지 탐색 |
| 과업명 열이 `담당 과제(세부 연구개발)` | `과업`뿐 아니라 `과제`도 인식 |
| 코드가 시트마다 1부터 다시 시작 | `기관명-코드`로 전역 고유화 |
| 일정이 `1~3월`인 마일스톤 시트가 섞임 | 날짜가 채워진 비율로 일정 시트인지 판정 |
| 기관마다 산정 기준이 다름(가중/계층) | 총괄시트 집계값이 있으면 **그 값을 그대로 사용** |

**계획(%)과 진척(%)은 반드시 갈라 읽는다.** 둘을 섞으면 이 사업의 핵심 지표인 차이(%p)가 사라진다. 정상/주의/지연 임계값(-5%p)은 검증 파일의 총괄시트 판정에서 역산해 맞췄다.

실제 파일로 검증한 결과 항목 수(226)와 기관별·전체 진척률이 파일의 자체 집계와 일치한다.

## 5. 기관별 원페이지 (`lib/orgPage.ts`)

**용도가 분명한 화면이다** — 해당 기관과 회의하거나 전화하기 직전에 여는 화면. 그래서
스크롤 없이 한 화면에 끝나야 하고, 담을 것을 고르는 기준도 하나다: *지금 통화에서 꺼낼 말인가.*

```
┌ 지엠티 (주관연구기관)                        기준일 2026-08-13 ┐
│  진척 62%(계획 70%, -8%p) · 지연 3건 · 미결 2건 · 최종 8월 8일 │
│  ■ 지연 과업(WBS)        ■ 미결 요청(내 업무)                 │
│  ■ 다음 마일스톤          ■ 최근 이력                          │
│  ▸ 요약 한 문단                                               │
└────────────────────────────────────────────────────────────┘
```

**WBS 축과 내 업무 축을 한 화면에서 붙이는 첫 기능이다.** 연결 키는 `orgId` 하나뿐이고,
과업 단위 자동 연결은 하지 않는다 — 지금 붙이면 틀린 연결이 조용히 쌓인다.

진척은 **WBS 총괄시트 집계값을 그대로 가져온다.** 다시 계산하지 않는다. **KIMST와
기타는 WBS에 시트가 없어 진척 블록을 비운다** — 억지로 0%를 보여주면 지연으로 오해된다.

'기타 / 미분류'도 원페이지를 만든다. 여기 항목이 쌓이면 별칭 보강 신호다.

**요청사항이 주인공이다.** 기관을 여는 이유가 대개 "그거 아직 답 안 왔는데"이기 때문에,
면적을 가장 크게 주고 맨 위에 둔다. 정렬은 기한이 아니라 **경과일 내림차순** —
오래 방치된 것이 위로 와야 한다. 8영업일을 넘기면 기관 임계일과 별개로 붉게 띄운다.

기관 선택은 버튼 11개를 늘어놓는 대신 **드롭다운**이고, 옵션에 미회신 건수가 붙어 고르기
전에 보인다. 아무것도 고르지 않으면 **미회신이 가장 많은 기관**이 열린다.

요약 문단에는 **집계값만 넘긴다.** 업무 원문을 통째로 넣지 않고, 3문장 이내로 제한하며,
수치는 그대로 인용하게 한다(모델이 재계산하지 않는다). 모델이 없으면 규칙 요약이 나오고
화면은 그대로 동작한다 — 요약은 이 기능의 마지막 층이지 전제가 아니다.

**다음 마일스톤은 근사값이다.** 전용 마일스톤 시트 파서가 아직 없어(일정이 `1~3월` 형태)
과업 시트의 마일스톤 표시·산출물 항목 중 안 지난 것을 뽑는다. 정확히 같지는 않지만
"다음에 뭐가 걸려 있죠"에는 답이 된다.

## 6. RFP 원문 검색 (`lib/rfp.ts`, `lib/rfpParse.ts`)

RFP를 넣고 검색어를 치면 **몇 쪽에 있는지**를 바로 찾는다. 왼쪽에 결과, 오른쪽에 본문이고, 결과를 누르면 그 쪽으로 넘어가면서 검색어가 강조된다.

**여기에는 LLM도 임베딩도 벡터DB도 쓰지 않는다.** 담당자가 원하는 건 "이 문구가 RFP 어디에 있나"이고 그건 일반 텍스트 검색으로 충분하다. 뒤에 `보고 생성`이 붙은 지금도 이 화면은 그대로다 — **모델을 넣을 수 있다는 것과 넣어야 한다는 것은 다르다.** 검색은 결과가 왜 그 순서인지 설명되어야 하고, 그건 규칙이 더 잘한다.

검색 라이브러리도 넣지 않았다. 필요한 랭킹 규칙이 명확해서 직접 계산하는 편이 짧고, 왜 이 순서로 나왔는지 설명할 수 있다.

```
"현장 실증" 검색 시
  정확 구문으로 붙어 있음      +100
  같은 문단 안에 둘 다 있음     +40
  같은 쪽에 각각 있음           +12
  등장 횟수                    +2/회 (상한 20 — 목차가 1위로 올라오지 않게)
```

여러 단어를 넣으면 **모두 포함된 쪽만** 남긴다(AND). 부분일치라 `데이터`로 `학습데이터`·`데이터셋`이 함께 걸린다.

**형식** — PDF는 원래 페이지가 있으므로 그대로 쓰고, DOCX·TXT는 문단 경계를 지키며 나눠 가짜 페이지를 만든다(문단 중간에서 자르면 검색 조각이 어색해지고 문단 점수도 틀어진다). HWP는 아직 못 읽으며 "PDF로 저장해 달라"고 분명히 알린다.

실제 CDX 심의자료 PDF로 확인했다. 5쪽 5,553자를 뽑아 `현장 실증`을 검색하면 두 단어가 같은 문단에 있는 4쪽(68점)이 각각 흩어진 5쪽(32점)보다 위에 온다. 스캔 이미지 PDF(306쪽인데 0자)는 "텍스트가 선택되는 PDF가 필요합니다"로 안내한다.

**다른 화면과 이어붙일 자리** — `/rfp?q=실증`로 들어오면 자동으로 그 검색어로 시작한다. 업무트리나 WBS에 "RFP에서 근거 찾기"를 붙일 때 이 주소만 알면 된다. 문서 구조도 `RfpPage[]`로 쪽 단위를 유지해 두어 페이지별 인용이나 원문 뷰어를 나중에 붙일 수 있다.

## 7. 보고 생성 — 로컬 LLM (`lib/llm.ts`)

**선별은 룰, 문장은 LLM.** 무엇을 보고할지 고르는 일은 기존 `lib/mytask.ts`의 우선순위
점수가 하고, LLM은 그것을 읽기 좋은 문장으로 바꾸는 역할만 한다. 선별까지 모델에
맡기면 "왜 이게 보고사항인지"를 설명할 수 없게 된다.

**모델은 로컬 Ollama만 쓴다.** 클라우드 API는 붙이지 않는다 — 자료가 브라우저를
벗어나지 않는다는 이 도구의 전제를 그대로 유지하기 위해서다.

```bash
brew install ollama
ollama serve            # 별도 탭에서 계속 실행 → localhost:11434
ollama pull qwen3:8b
```

모델·주소·컨텍스트 길이는 `보고 생성` 화면의 설정에서 바꾼다. Ollama가 떠 있지
않아도 화면은 그대로 동작한다 — 규칙으로 만든 문장으로 떨어질 뿐이다.

### 지키는 경계

- **자동 호출 없음.** 버튼을 눌렀을 때만 모델이 돈다.
- **무엇이 나가는지 보여준다.** 각 화면의 `모델에 보낼 원문 보기`로 입력을 미리 확인한다.
- **근거를 함께 띄운다.** 생성된 문장 밑에 어느 업무·어느 안건에서 나왔는지가 붙는다.
- **카테고리를 늘리지 않는다.** 모델이 새 분류를 만들지 못하게 스키마로 고정한다.
- **LLM 문장과 규칙 문장을 구분해 표시한다.** 화면의 `LLM` / `규칙` 배지가 그것이다.

### `num_ctx`가 이 작업의 1번 함정

Ollama 기본값은 4096이다. 이대로 2만 자 회의록을 넣으면 **에러 없이** 앞부분만 읽고
그럴듯한 요약을 뱉는다. 뒤쪽 안건이 통째로 사라지는데 화면상으로는 멀쩡해 보인다.
그래서 `buildRequest`가 `num_ctx`를 항상 싣고, 그 사실 자체를 테스트로 고정해 뒀다.

### 일일 업무보고 (`lib/dailyReport.ts`)

```
등록된 업무 전체
  → [룰] 보고 대상 선별 (mytask.ts 점수 재활용)
  → [룰] 상부 / 연구책임자 분류
  → [LLM] 구두로 말하기 좋은 문장으로 변환
  → 화면 표시 (각 항목에 근거 업무 표시)
```

| 선별 조건 | 분류 |
|---|---|
| 긴급 등급 · 기한 초과/오늘/내일 | **상부 구두보고** — 예산 대응 · 마일스톤 · 보고자료 작성 |
| 2회 이상 미뤄짐 | **연구책임자 전달** — 데이터 수급 · 진도관리 · 실증·성과관리 · 회의 후속조치 |
| 외부기관 회신 대기 · 다음 회의 전 확정 필요 | **양쪽** — 지연 과업에 직접 영향(`blocksRnd`) · 기한 초과 |

**입력 개수 = 출력 개수를 코드가 보장한다.** 모델이 항목을 합치거나 없는 id를 지어내도,
결과는 룰이 고른 목록 기준으로 다시 맞춰진다. 모델이 빠뜨린 항목은 규칙 문장으로 채운다.

### 이메일 초안 (`lib/emailDraft.ts`)

공문·요청 메일은 형식이 정해져 있어 구조는 템플릿으로 충분하다. LLM은 메모투 문장을
정중한 본문으로 바꾸는 부분만 맡는다.

```
[템플릿] 수신 · 제목 · 인사 · 배경 · 요청사항 · 기한 · 회신처 · 맺음
              ↑                    ↑
           룰로 채움           LLM이 문장 생성
```

**기관명·날짜는 모델 출력에서 받지 않는다.** 원본 업무 데이터에서 주입한다 — 8B급
모델이 가장 자주 지어내는 게 이 둘이라 통로를 아예 막았다. 생성 결과는 반드시 편집
화면을 거치고, **발송 버튼은 만들지 않았다.**

few-shot 예시(`DEFAULT_EMAIL_EXAMPLES`)를 **실제로 보냈던 메일 3통으로 갈아끼우면**
공문체 품질이 눈에 띄게 오른다. 8B 모델의 어색한 문장은 대부분 예시로 해결된다.

### 사업 주간보고서 (`lib/weeklyReport.ts`, `lib/llmContext.ts`)

주간 산출물이 둘이다. **용도가 다르다** — 이건 사업 단위로 한 주를 정리한 **문서 한 장**이고,
아래 주간업무계획은 청 문서에 낄 **항목 한 건**이다. 서식도 분량 규칙도 달라 나눠 뒀다.

```
[CDX 연구개발사업] 주간업무계획 (2026.08.10 ~ 08.16)

□ 추진배경
  ○ …
□ 주요내용
  ○ …
□ 향후계획
  ○ …

※ 생성된 초안입니다. 숫자·기관명은 반드시 확인하세요.
```

**골격은 코드가 만든다.** 타이틀·섹션 헤더·말미 안내문은 고정 문자열이고, LLM은 각
섹션의 `○` 항목 내용만 만든다. 그래서 **모델이 죽어도 네 요소가 절대 빠지지 않는다.**
데이터가 없는 섹션은 지우지 않고 `○ 해당 없음`으로, 생성이 실패하면
`○ (생성 실패 — 직접 작성)`으로 채운다. 섹션이 사라지는 경로가 없다.

**원본을 통째로 넣지 않는다.** `llmContext.ts`가 요약본만 만든다(상한 3,000토큰).

| 넣는 것 | 빼는 것 |
|---|---|
| 사업 기본정보 · 주간 범위 | WBS 전체 행 |
| WBS 집계 숫자 · 기관별 진척 | RFP 원문 |
| 지연 상위 10건 · 주의 상위 5건 | 완료된 과업·업무 |
| 이번 주 / 다음 주 업무 · 미해결 쟁점 · 마일스톤 3건 | 한 달 밖 일정 |

상한을 넘으면 **줄 단위로** 자르고 잘렸다고 남긴다 — 문장 중간에서 끊으면 모델이 잘린
조각을 사실로 읽는다. 빈 절도 `해당 없음`으로 남긴다. 없다는 사실을 알아야 지어내지 않는다.

### 주간업무계획 — 항목 단위 (`lib/weeklyPlan.ts`)

다른 기능과 성격이 다르다. **여기서는 분량 자체가 형식이다.** 해양경찰청 주간업무계획
3개 호(업무계획 117건)의 한글 파일 줄배치 캐시를 실측해 만든 예산이라, 넘기면 목록
정렬이 실제로 깨진다.

| 라인 | 권장 상한 | 비고 |
|---|---|---|
| 제목 `①…` | 80폭 | 반드시 1줄 (53건 전부 1줄) |
| 본문 `- (라벨)` | 78폭 또는 100~143폭 | **82~99폭은 금지 구간** |
| 각주 `*` `※` | 95폭 | 반드시 1줄 |

금지 구간은 1줄로 끝나지도 2줄을 채우지도 못하는 폭이다. 걸리면 오른쪽에 빈 공간이
크게 남는다.

그래서 이 기능만 **생성 → 검증 → 재생성 루프**를 돈다.

**등록된 보고사항을 그 서식으로 뽑는다.** 빈 폼에 사실관계를 옮겨 적게 하면 업무트리에
이미 있는 내용을 두 번 쓰게 된다. 업무를 고르면 기관·기한·상태와 **지연 이력이 그대로
재료가 된다** — "당초 6월 30일 → 현재 9월 30일 (1회)", "회신 대기 8월 7일 요청,
4영업일 경과". 이력에 없으면 없는 대로 두고 경위를 지어내지 않는다.

**서식은 9종이고 원문 빈도순으로 둔다.** 자주 쓰는 것이 위에 있어야 한다.

| 서식 | 건수 | 골격 |
|---|---|---|
| 계획수립 | 36 | 제목 + 본문 1~3 + 각주 0~2 |
| 교육·훈련 | 19 | 제목 + 본문 + 각주 |
| 점검·조사·분석 | 17 | 제목 + 본문 + 각주 |
| **기타일정** | 17 | **제목 + 각주 0~1개 — 본문 없음** |
| 인력·조직 운영 | 14 | 제목 + 본문 + 각주 |
| 사업추진·시스템구축 | 10 | 제목 + 본문 + 각주 |
| 법령·제도 제개정 | 8 | 3단 구성 필수 |
| 회의·행사 개최 | 7 | 배경 생략 · 일시/장소 각주 필수 |
| 연구용역·R&D | 6 | 3단 + 화살표 일정 |

**업무성과(지난주 실적)는 넣지 않았다.** 이 앱이 다루는 건 사업 진행사항이고, 성과
정리는 다른 자료에서 온다. 기타일정은 라인 구성이 달라(제목 + 각주뿐) 업무계획
검증기를 그대로 대면 "본문 라인 없음"으로 떨어지므로 골격별로 나눴다.

**유형 판정은 규칙이 한다.** 업무계획 8종은 제목 키워드로 고르고 그 유형의 프롬프트와
few-shot 2개만 준다. 모델에 맡기면 라벨 조합이 매번 흔들린다. 국(局)별 관행(번호 기호·
라벨 구성·각주 머리기호)도 표로 고정돼 있다 — 수사국만 `➀➁➂➃`를 쓰는 것까지 그대로다.

**분량은 프롬프트만으로 안 맞는다.** 소형 모델은 한국어 표시폭을 세지 못한다. 그래서
재생성 프롬프트는 "줄여라"가 아니라 **"현재 92폭 → 80폭 이하로 12폭 줄일 것"** 처럼
숫자로 알려준다. 최대 3회까지 돌리고, 그래도 안 맞으면 마지막 초안과 위반 목록을 함께
남긴다 — 사람이 고칠 수 있어야 하기 때문이다.

**기호는 후처리로 강제한다.** `➊➋➌` · `→` · `’26년`은 모델이 자주 틀린다. 다만
**줄 맨 앞의 번호는 항목 번호이므로 원문자(①)로 바꾼다** — 여기서 불릿으로 바꾸면
제목 라인이 통째로 형식을 벗어난다(qwen3:8b에서 실제로 걸린 문제다).

검증기는 원문 87개 항목에 그대로 적용했을 때 71% 통과였다. 실패한 25건은 대부분 실제
예외 사례라, **이 검증기는 실제 문서보다 약간 엄격하다.** 생성물은 늘 원문보다 느슨하게
나오므로 초안 가이드로는 이 정도가 맞다.

> **이 기능만 더 큰 모델이 필요하다.** `qwen3:8b`로는 개조식 서식을 지키지 못해
> 재생성을 반복한다. `qwen2.5:14b-instruct` 이상 또는 `exaone3.5:7.8b` 계열을 권장한다.

### 인수인계서 (`lib/handover.ts`)

**전제가 하나 있다.** 담당자가 바뀔 때 크게 유실되는 것은 진행 중 과업 목록이 아니다.
그건 업무트리를 열면 보인다. 유실되는 것은 **"왜 이 상태인지"** — 당초 6월이던 기한이
왜 9월이 됐는지, 그 연기에 무슨 사정이 있었는지다.

**여섯 절 중 다섯은 조립이고 LLM은 `사업 개요` 한 단락뿐이다.**

| 절 | 어디서 오나 |
|---|---|
| ① 사업 개요 | **LLM (집계값만 넘김, 3문단)** |
| ② 진행 중 과업 | WBS 지연·주의 + 내 업무 |
| ③ 미결 요청사항 | 이벤트 로그의 회신 대기, 오래 기다린 것부터 |
| ④ 기관별 특이사항 | 2회 이상 밀린 항목의 경위 |
| ⑤ 다가오는 일정 | WBS 마일스톤·산출물 |
| ⑥ 주요 쟁점 | 회의록에서 온 미해결 쟁점 |

앞선 판은 세 절을 전부 LLM으로 문장화했는데, 그러면 **모델이 죽을 때 문서의 대부분이
규칙 문장으로 떨어진다.** 담당자가 바뀌는 날 열어보는 문서가 모델 사정에 좌우되면
곤란하다. 그래서 뒤집었다 — 실패해도 다섯 절은 그대로 나오고 개요만 비는 걸 테스트로 고정했다.

지켜야 할 선이 둘 있다.

**기록되지 않은 사유를 지어내지 않는다.** 사유가 없는 연기는 `사유 미기재`로 그대로 둔다.
인수인계서는 나중에 근거 문서가 되기 때문이다.

**기관을 평가하지 않는다.** "A기관 대응이 느림" 같은 문장이 문서로 남으면 곤란해진다.
사실만 적는다 — "2회 연기, 당초 6월 30일 → 현재 9월 30일, 사유 미기재".

출력은 **플레인 텍스트**다. HWP·PDF 렌더링은 하지 않는다 — 받는 사람이 어디에든
붙여 넣을 수 있어야 한다. 복사와 `.txt` 저장을 붙였다.

### 재촉 메일 (`lib/reminder.ts`)

새 파이프라인이 아니다. **입력이 다를 뿐 이메일 초안과 같은 길을 간다.** 다른 점은 둘이다.

**단계가 있다.** 같은 재촉이라도 3차와 1차의 문장이 같으면 안 된다.

| 차수 | 문체 | 마무리 |
|---|---|---|
| 1차 | 확인 요청 | "8월 7일에 요청드린 건입니다. 진행 상황 확인 부탁드립니다." |
| 2차 | 기한 명시 | "8월 20일까지 회신 부탁드립니다." |
| 3차 | 경위 명시 | "당초 8월 7일에 요청드린 건으로 4영업일째 회신을 기다리고 있습니다…" |

**경위는 계산하지 않고 주입한다.** 당초 요청일·경과 영업일·기한은 전부 이벤트 로그에서
나오고, 프롬프트는 모델에게 **날짜를 쓰지 말라고 명시한다.** 모델에게 날짜를 세게 하면
반드시 틀린다.

판정은 기관별 임계일(주관 3 · 공동 5 · 전문 7영업일)을 넘겼는지 하나다. 회신이 왔으면
아무리 오래 걸렸어도 대상이 아니다.

**발송 버튼은 없다.** 대신 `발송함`을 눌러야 `reminded`가 기록되고 목록에서 빠진다 —
누르지 않으면 내일 같은 항목이 또 뜬다. 실제로 보냈는지는 사람만 알기 때문이다.
기록하면 그날은 목록에서 사라지고, 임계일이 다시 지나면 다음 차수로 돌아온다.

### 회의록 (`lib/minutes.ts`)

8B 모델의 최대 약점은 긴 입력의 뒷부분을 조용히 흘리는 것이다. 그래서 한 번에 던지지 않는다.

```
회의록
  → [룰] 안건 경계로 분할 ("1. ", "가.", "안건", "○" 등)
  → [LLM] 안건마다 개별 호출 → 쟁점·결정·액션 추출
  → [룰] 병합 후 1페이지 구성 (템플릿, LLM 없음)
```

호출이 5~10회로 늘어 30초~1분 걸리지만 실시간 작업이 아니다. 팬 없는 맥북에어에서
병렬로 돌리면 클럭이 떨어져 오히려 느려지므로 **순차로 돌리고 진행률만 표시한다.**

`sourceSegment`가 이 기능의 핵심이다. RFP 검색의 "몇 쪽에 있는지"와 같은 철학으로
**어느 발언에서 나온 결론인지** 되짚을 수 있어야 한다. 그래서 세그먼트 번호는 모델
출력에서 받지 않고 호출한 쪽이 붙인다 — 모델이 번호를 지어낼 여지를 없앤다.

회의 제목·일시·참석자도 규칙으로 뽑는다. 정해진 자리에 적혀 있는 값이고, 모델에
맡기면 참석자 이름을 가장 먼저 지어낸다. 머리말 블록은 안건으로 세지 않는다 —
남겨 두면 호출이 한 번 늘고 안건 번호가 통째로 한 칸씩 밀린다.

**모델이 돌려준 기한은 원문에 실제로 적혀 있을 때만 받는다.** qwen3:8b는 "이달
말까지"를 8월 31일로 바꿔 온다. 그럴듯하지만 이건 모델이 한 날짜 계산이고, 이 앱은
빠른 입력부터 **날짜를 추측하지 않는다**는 규칙을 지켜 왔다. 근거 없는 날짜는 버리고
기한 미정으로 남긴 뒤 사람이 채우게 한다(`dateGroundedIn`).

추출된 후속조치는 기존 빠른 입력(`lib/capture.ts`)을 통해 **업무로 바로 등록된다.**
회의록 → 업무 자동 등록이 이 기능의 진짜 값어치다.

#### 요청사항 — 방향이 있다

후속조치와 다른 점은 **방향**이다. 우리가 요청한 건과 요청받은 건은 이후 판정이 갈린다 —
나간 건은 회신 대기(재촉 대상)가 되고, 받은 건은 내가 처리할 일(기한 임박 대상)이 된다.

**모델이 정하는 것은 방향과 문장뿐이다.**

| 값 | 누가 정하나 |
|---|---|
| `direction` | 모델 (문장의 의미라 규칙으로 못 읽는다) |
| `text` | 모델 |
| `counterpartOrgId` | **별칭 매칭** — 모델이 다른 기관을 우겨도 문장에 있는 기관을 쓴다 |
| `categoryId` | **기존 8개 분류기** — 모델이 새 분류를 만들지 못한다 |
| `due` | **원문 근거 검사** — 원문에 없는 날짜는 버린다 |
| `confidence` | **빈 칸 여부** — 기한이나 기관이 비면 `low` |

**일괄 자동 등록을 하지 않는다.** 기본값은 전체 선택 해제다 — 회의록에서 뽑은 것이 전부
내 업무는 아니다. `confidence: low`는 화면에서 흐리게 표시하고 체크를 비워 둔다.

등록된 업무에는 회의명과 안건 번호가 근거로 남아 **회의록 해당 발언으로 되짚어 갈 수 있다.**

한 안건이 실패해도 나머지는 계속 돌고, **실패한 안건 번호를 보고서에 남긴다** —
조용히 빠지는 것이 가장 나쁘다.

## 배포

Vercel에 그대로 올라간다(설정 파일 없음). 다만 **LLM 기능은 배포한다고 따라오지 않는다.**

브라우저가 `localhost:11434`를 부르는 구조는 그대로지만, 페이지 출처가 배포 도메인으로
바뀌면 Ollama가 **서버가 켜져 있어도** 403을 돌려준다. 실측한 값이다.

```
Origin: http://localhost:3000        → 200 OK
Origin: https://<배포주소>            → 403 Forbidden
```

쓰려면 각자 자기 컴퓨터에서 Ollama에 그 출처를 허용해 줘야 한다.

```bash
OLLAMA_ORIGINS="https://<배포주소>" ollama serve
```

그래서 `보고 생성` 화면은 페이지 주소를 보고 안내를 바꾼다 — 로컬이면 `ollama serve`를,
배포 주소면 `OLLAMA_ORIGINS`를 알려 준다(`connectionHint`). 틀린 곳을 가리키는 안내가
가장 오래 헤매게 만들기 때문이다.

**RFP 검색·연구개발 현황·업무트리는 배포판에서 아무 설정 없이 그대로 동작한다.** 보고
생성도 화면은 열리고, 모델이 없으면 규칙 문장으로 떨어진다.

> 공개 주소로 올리면 누구나 앱에 접근할 수 있다. 데이터는 각자 브라우저에만 남으므로
> 자료가 새지는 않지만, 기관 도입 단계에서는 위에 적은 계정·권한 통제가 먼저다.

**원칙 1** — 시간에 의존하는 함수는 전부 `today`를 인자로 받는다(`capture`, `score`, `bucket`, `summarize`, `generateDailyReport`, `generateMinutes`). 그래야 "오늘 기준"이 테스트 가능해진다.

**원칙 2** — `lib/`는 React를 import하지 않는다. 도메인 로직이 화면과 분리돼 있어야 Node에서 그대로 테스트할 수 있다. LLM 기능도 마찬가지로, `lib/`은 호출 함수(`LlmCall`)를 인자로 받을 뿐 Ollama를 직접 알지 않는다 — 그래서 테스트에서 가짜 응답을 넣어 스키마 위반·타임아웃을 그대로 재현할 수 있다.

**원칙 3** — CSS는 토큰(`--surface`, `--text-2`, `--accent`, `--s4`…) 위에만 쌓는다. 색상 리터럴을 컴포넌트에 직접 쓰지 않아 라이트/다크가 자동으로 따라온다.

**LLM이 생성한 문장 자체는 테스트하지 않는다.** 매번 달라지므로 테스트 대상이 될 수 없다.
대신 **스키마에서 벗어난 응답이 왔을 때 앱이 죽지 않는지**를 테스트한다 — 모델이 사과문을
돌려주든, 항목을 지어내든, 중간에 죽든 보고서는 나와야 한다.

개발 중 테스트가 실제로 잡아낸 것들:

- `다음 주 화요일`이 요일에 따라 한 주 밀림 (오늘+N일 계산의 한계)
- `결과보고서`의 '과'가 기관명으로 인식됨
- `예산 설명자료 작성`이 예산 대응이 아니라 보고자료로 분류됨 → 카테고리 검사 순서 조정
- `이번 주까지 요청`이 요청이 아니라 확인으로 분류됨 → 상태 규칙 정비
- 엑셀 날짜가 자정에서 8초 어긋나 있어 잘라내면 `2026-01-01`이 `2025-12-31`이 됨 → 반올림
- 코드 매핑 시트의 *안내 문장*이 헤더로 오인됨 → 헤더 행 판정에 길이·칸 수 조건 추가

qwen3:8b로 실제 돌려 보고 잡은 것들:

- 회의록 머리말(회의명·일시·참석자)이 안건 1로 잡혀 호출이 한 번 늘고 안건 번호가 전부 한 칸씩 밀림
- 모델이 "이달 말까지"를 `2026-08-31`로 바꿔 보냄 → 원문에 없는 날짜를 버리는 검증 추가
- 줄바꿈 없이 붙여넣은 긴 회의록이 줄 경계로는 안 잘려 그대로 통째로 나감 → 문장·글자 수 순으로 물러서게 함

## 데이터 처리

모든 처리는 **브라우저 안에서만** 이뤄진다. 업로드한 WBS는 서버로 전송되지 않고, 등록한 업무는 `localStorage`에만 저장되며 JSON으로 내보내고 되돌릴 수 있다.

LLM도 마찬가지다. **로컬 Ollama(`localhost:11434`)만 호출하고 클라우드 API는 붙이지 않는다.** 다만 회의록에는 기관 평가·지연 사유·발언자 실명이 섞이므로, 무엇이 모델에 들어가는지 각 화면에서 미리 볼 수 있게 했다.

이건 데모라서 생략한 게 아니라 의도한 경계다. 다만 **기관 도입 단계에서는 부족하다.** 원본이 공개자료여도 앱 안에서 만들어지는 담당자 메모·지연 사유·기관 평가는 비공개 정보가 되기 때문이다. 실제 투입 전에는 계정·MFA·역할 권한, 사업별 데이터 분리, 변경 이력과 감사 로그, 업로드 파일 검사와 암호화가 먼저 필요하다.

## 알려진 한계

- 사업은 1개만 다룬다. 여러 사업은 `store` 키를 사업별로 나누면 확장된다.
- WBS 파일 내용은 저장하지 않는다(새로고침하면 다시 넣어야 함). 등록한 업무만 저장된다.
- 마일스톤 시트(완료기준 Gate, 증빙·산출물)는 아직 읽지 않는다. 일정이 `1~3월` 형태라 별도 파서가 필요하다 — 다음 단계로 가장 값어치 있는 항목이다.
- 업무와 WBS 과업이 자동으로 연결되지 않는다. 지금은 `blocksRnd` 플래그를 문장에서 추정할 뿐이다.
- 아이콘 원본이 투명 배경이 아니라 흰 배경이고 물개 얼굴도 흰색이다. 흰색을 투명으로 빼면 얼굴이 뚫리므로, 이미지는 그대로 두고 화면에서 흰 판으로 받쳐 다크 테마 시인성을 확보했다.
- RFP 뷰어는 추출한 텍스트를 보여준다. PDF 원본 페이지 렌더링은 넣지 않았고, 쪽 단위 구조를 유지해 뒀으니 필요하면 그 위에 붙이면 된다.
- 아주 긴 RFP는 브라우저 저장 한도를 넘을 수 있다. 그때는 업무 기록을 지키기 위해 RFP만 저장에서 빼고, 화면에서는 그대로 쓴다(새로고침하면 다시 넣어야 함).
- **8B로는 회의록 품질이 아쉽다.** 청킹으로 우회하고 있으며, 여유가 생기면 `gpt-oss:20b`로 바꾸면 된다 — Ollama는 모델명만 바꾸면 되므로 코드 변경이 없다. 그래서 프롬프트와 스키마를 먼저 확정했다.
- **팬 없는 맥북에어의 발열.** 연속 호출 시 3~4분째부터 클럭이 떨어져 뒤로 갈수록 느려진다.
- 메일 few-shot 예시가 아직 **자리만 채운 기본값**이다. 실제로 보냈던 메일 3통으로 갈아끼우기 전까지는 공문체가 조금 밋밋하다.
- 회의록에서 뽑은 후속조치는 담당·기한이 비어 있을 수 있다. 원문에 없으면 채우지 않기 때문이며, 업무로 등록한 뒤 사람이 채우는 걸 전제로 한다.
- **32B급이 필요해지면 담당자 노트북에서 못 돈다.** 사업부 서버 한 대가 전제가 된다.
- LLM 기능이 붙으면서 기관 도입 시의 전제가 더 무거워졌다. 회의록의 비공개 정보를 다루게 되므로 위에 적은 계정·MFA·역할 권한·감사 로그가 **선택이 아니라 필수**가 된다.
